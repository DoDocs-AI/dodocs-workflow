Scrum Team Pipeline

One human sentence goes in. A reviewed, tested pull request comes out. Between them sit six phases, thirteen agents and eleven gates — the lead only coordinates and never writes code.

The artifact chain

The phases below run agents; this is what actually moves between them. Every box is a file on disk, every arrow is the agent that writes it, and every orange bar is a gate that has to pass before the next box exists.

Boot — before Phase 1

Everything here happens on main, before a single line of the feature exists. If openspec/ is missing the command stops and tells you to run /spec-bootstrap.

Parse flags --auto, --size s/m/l, --retest, --skip-regression. No size flag → guessed from the feature name.
Read config .claude/scrum-team-config.md — paths, ports, compile and lint commands. Missing → stop.
Regression baseline Run the existing E2E suite on main and record what already fails, so old failures never block the new PR.
Branch git checkout -b feature/<slug>, then create PROGRESS.md — the shared dashboard every agent writes to.

The six phases

01

Requirements + early UX research

⏱ 15 min∥ 2 agents

Skipped when /prepare-feature already left an approved change — then only UX research runs.

∥ parallel
product-owneropus

Interviews you — or derives requirements alone under --auto — and self-validates the result.

◂ human requirements
▸ openspec/changes/<slug>/ proposal.md + delta specs

ux-designersonnet

Reads the existing UI first. Produces no document yet — this is pattern reconnaissance.

◂ existing pages + components
▸ pattern research held in context

gate↻ openspec validate <slug> --strict must exit 0 and ## Why must be non-empty — otherwise product-owner is re-spawned with the validator output.
02

UX design + architecture

⏱ 20 min∥ 2, then ↓ 2

Whole phase is skipped at --size small. The architect runs in plan mode only for a manual large feature.

∥ parallel — the architect does not wait for UX
ux-designersonnet

Turns Phase 1 research plus the change into flows, states, keyboard and responsive behaviour.

◂ proposal + deltas + research
▸ UX-DESIGN.md

architectopus

Reads real code patterns before designing. Endpoints, entities, components, file inventory.

◂ proposal + deltas + codebase
▸ design.md

↓ then, sequentially — skipped if daytime-prep mockups exist
mockup-designersonnet

Builds screens from the project's own components — not sketches, real framework code.

◂ change + UX-DESIGN.md
▸ mockups/*.tsx + Vite server on :3100

mockup-validatorsonnet

Cross-checks every screen against the change. One retry on failure, then the workflow moves on.

◂ mockups + proposal
▸ MOCKUP-VALIDATION.md

gate↻ design.md needs endpoints or components and a File Inventory; UX-DESIGN.md needs at least one flow. Missing → the author is re-spawned.
human● The one stop for a person: open localhost:3100, review flows, architecture and screens, approve. --auto skips it.
03

Task breakdown

⏱ 10 min↓ 1 agent

The only phase that is deliberately single-threaded — one writer prevents two devs owning one file.

scrum-mastersonnet

Writes the canonical checklist, then creates the live tasks from it under three hard rules: only backend-dev-1 owns migrations, no two devs touch the same file, and dependencies are declared with blockedBy.

◂ design.md + delta specs
▸ tasks.md + one task per unit of work, prefixed [US01]

gate↻ At least 2 developer tasks, every subject carrying a user-story prefix, and tasks.md mirroring them. Short → scrum-master runs again.
04

Build + test

⏱ 120 min∥ up to 8 agents

The long phase. Everything below runs at once, and testing starts per story rather than at the end.

∥ all parallel
frontend-dev-1 · 2sonnet

One atomic commit per task, then tick the matching box in tasks.md. Dev 2 only at medium and large.

▸ commits · pages, components, services

backend-dev-1 · 2sonnet

Dev 1 owns every migration; dev 2 never writes one and is blocked until dev 1's migration lands.

▸ commits · endpoints, entities, migrations

qa-engineersonnet

Writes test cases per user story ahead of the code, so testing is never the bottleneck.

▸ test-case .md files + AC traceability matrix

code-reviewersonnet

Watches for finished tasks and reviews each one individually — patterns, security, edge cases.

▸ approval or change request per task

tech-leadsonnet

Runs the compile gate, starts the app, watches it for runtime breakage and files bugs as tasks.

▸ "app ready" signal · bug tasks

manual-testerhaiku

Drives a real browser. Starts a story the moment that story is reviewed and its cases exist.

▸ pass/fail per scenario · bugs with screenshots

qa-automationsonnet

Follows the tester one story behind, writing Playwright specs only for what already passed by hand.

▸ E2E specs per story

compileBackend builds · frontend builds · lint clean · app reachable. Only then does tech-lead release testing.
05

Integration verification

⏱ 30 min∥ 4–6 agents

The feature is done story by story; this asks whether it holds together as one thing.

∥ parallel
tech-leadsonnet

Full restart from cold, then a regression sweep against the boot baseline.

▸ regression verdict

qa-automationsonnet

Runs the whole E2E suite. Failures present in the baseline do not count against the PR.

▸ suite result vs baseline

manual-testerhaiku

One end-to-end pass through the complete feature flow, not story fragments.

▸ smoke test result

code-reviewersonnet

Reviews the entire branch diff at once — what per-task review can't see.

◂ git diff origin/main...HEAD

quality-metrics-collectorsonnet

Lines changed, test-to-code ratio, AC coverage, file complexity, against pass/warn/fail thresholds.

▸ QUALITY-METRICS.md

security-auditoropus

Conditional — spawned only when the diff touches auth, sessions, tokens, CORS, roles, migrations, routes, middleware or secrets.

▸ findings by severity

stop⛔ Any Critical security finding halts Phase 6. Fix tasks are created and the auditor runs again. Every gate in PROGRESS.md must read PASS before shipping.
06

Ship

⏱ 10 min↓ 1 agent

openspec archive deliberately does not run here — it happens post-merge on main, via /ship.

tech-leadsonnet

Ticks every remaining box in tasks.md, walks the ten Definition-of-Done checks, and opens the PR with a rollback plan in the description.

▸ pull request → main · PR URL written back into PROGRESS.md

The loop inside Phase 4

Stories do not queue behind each other. US01 can be in retest while US02 is still being written — which is why a bug never stalls the whole feature, and why a stubborn one has an escape hatch.

developer finishes a task ──▸ atomic commit │ ▾ code-reviewer reviews that task alone │ ▾ per story — no waiting on other stories all US01 tasks reviewed + US01 test cases ready │ ▾ manual-tester tests US01 now │ ├── pass ──▸ qa-automation writes the E2E spec for US01 │ └── fail ──▸ bug task ──▸ developer fixes ──▸ review ──▸ retest ─┐ ▴ │ └─────────────────────────────────────────────────┘ same case fails twice ──▸ escalate to tech-lead meanwhile: US02 is still being built ──▸ reviewed ──▸ tested ──▸ …

Definition of Done

Ten checks the tech-lead walks before gh pr create. One failure, no PR.

01Tasks closed — zero open dev tasks, all reviewer-approved
02Compile clean — backend and frontend, zero errors
03Lint clean — using the command from project config
04Manual tests pass — every story green in PROGRESS.md
05E2E pass — the suite qa-automation produced runs green
06No P0 bugs — zero open Critical bug tasks
07AC traceability — every acceptance criterion marked Full
08PROGRESS.md current — no stale Pending rows
09No scope creep — diff stat holds no unexpected files
10Integration verified — all of Phase 5 came back green

Retest mode

/scrum-team --retest <feature>

A separate, much shorter shape for a feature that already exists. Phases 1–3 are skipped entirely, no branch is created, and five agents spawn at once against the test cases already on disk: R1 tech-lead brings the app up and runs the compile gate, R2 the tester works every scenario while both devs stand by, R3 bug → fix → review → retest until nothing fails.

tech-lead code-reviewer manual-tester frontend-dev-1 backend-dev-1

Drawn from claude/commands/scrum-team.md and the agent definitions in claude/agents/ at v2.0.0. Model assignments come from each agent's own frontmatter, which differs from the summary line in the command doc — that line claims opus for the architect and security-auditor and sonnet for everyone else, while product-owner.md declares opus and manual-tester.md declares haiku. Timeouts are the phase limits the lead tracks; under --auto they log a warning rather than stopping the run.
